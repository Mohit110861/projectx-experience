Part 1 — The big picture

1.1 What this website is

Project X Experience is an event booking website. Visitors can see upcoming parties, look at photos and reels, create an account and request a spot at an event. The admin (you) approves requests, records payments, blocks bad users, uploads photos and reels, edits the top header, and downloads an Excel sheet of everyone who paid.

In simple words: it is like a mini "BookMyShow" made only for Project X parties, with a control room (the admin dashboard) where you manage everything.

1.2 The three layers

The website is split into three parts that work together. Each part runs separately on your computer.

  • Frontend (client) — the pages in the browser: home page, event page, login, admin dashboard. Built with React (a JavaScript library for building pages out of small pieces called components) and styled with Tailwind CSS.
  • Backend (server) — a program that receives requests from the frontend, checks who is asking (login), applies the rules ("you can't book a past event"), and reads/writes the database. Built with Node.js and Express.
  • Database (MySQL) — stores everything permanently: users, events, bookings, gallery photos, reels and site settings, in tables (like Excel sheets).
Example: when you open the home page, React asks the backend "give me all events" (GET /api/events). The backend reads the events table in MySQL and sends the list back. React then draws the event cards.

1.4 How to start the website

  1. Make sure the MySQL80 service is running (it starts with Windows on your PC).
  2. Open the EVENT folder in VS Code and open a terminal.
  3. Run npm run dev. This starts the backend (port 5000) and the frontend (port 5173) together.
  4. Open http://localhost:5173 in the browser.
CommandWhat it does
npm run devStarts both parts in development mode (auto-reload when you edit code).
npm run seed --prefix serverDeletes users/events/bookings and refills them with demo data. Gallery, reels and header settings are not touched.
npm run buildMakes an optimised version of the frontend for putting online.
npm run install:allInstalls all libraries for server and client (first time only).
Demo logins: admin@eventora.com / password123 (admin) and user@eventora.com / password123 (normal user).

1.5 The database tables

The database is called eventora. It has 7 tables. Think of each table as an Excel sheet: rows are records, columns are fields.

TableWhat it storesImportant columns
usersEveryone with an account, including admins.name, email (unique), password (scrambled), role (user/admin), is_verified, is_blocked, phone
eventsEvery party, past and upcoming.title, description, date, location, category, total_seats, available_seats, image, ticket_price, created_by
bookingsA user's request for a spot at an event.user_id, event_id, status (pending/confirmed/cancelled), payment_status (paid/not_paid), amount, payment_method, payment_ref, paid_at
otps6-digit codes for sign-up and booking. Valid 5 minutes.email, otp, action (account_verification / event_booking), created_at
galleryPhotos shown in "The Gallery".image_url, caption, sort_order
reelsReels shown in the "Reels" row.title, video_url, cover_url, instagram_url, sort_order
settingsHeader & site text (one row per setting).setting_key, setting_value — e.g. announcement_text, hero_image

How tables connect: a booking points to one user (user_id) and one event (event_id). These links are called foreign keys. If an event is deleted, its bookings stay but show "Deleted event". If a user is deleted, their bookings are deleted too.

Slots: total_seats is how many spots the event has. available_seats goes down by 1 only when the admin confirms a booking, and goes back up if a confirmed booking is cancelled. A request that is only "pending" does not use a slot yet.

2.1 Settings & startup files

server/server.js

46 lines · the starting point of the backend

This is the first file that runs. It sets up Express (the web server library), plugs in all the routes, and connects to MySQL.

  • app.use(cors()) — allows the website on port 5173 to talk to the server on port 5000.
  • app.use(express.json()) — lets the server read JSON data sent by the website.
  • Plugs in the five route files: /api/auth, /api/events, /api/bookings, /api/admin, and /api (gallery, reels, settings).
  • /uploads — makes uploaded photos and videos downloadable by the browser.
  • initDB() — creates the database and tables if missing, then starts listening on port 5000. Every minute it deletes expired OTP codes.
initDB()
  .then(() => {
    console.log('MySQL Connected');
    setInterval(() => OTP.cleanupExpired().catch(() => {}), 60 * 1000); // clean old OTPs
    app.listen(PORT, () => console.log(`Server running on port ${PORT}`));
  })
  .catch(err => { console.error('MySQL Connection Error:', err.message); process.exit(1); });
In simple words: "Open the shop: connect to the database, then start answering customers."

server/schema.sql

87 lines · the design of every table

Written in SQL (the language of databases). Each CREATE TABLE IF NOT EXISTS block designs one table: column names, types and rules. "IF NOT EXISTS" means it never deletes existing data — it only creates tables that are missing.

CREATE TABLE IF NOT EXISTS bookings (
    id              INT AUTO_INCREMENT PRIMARY KEY,   -- 1, 2, 3 ... automatic
    user_id         INT NOT NULL,                     -- who booked
    event_id        INT NULL,                         -- which event
    status          ENUM('confirmed','cancelled','pending') DEFAULT 'pending',
    payment_status  ENUM('paid','not_paid') DEFAULT 'not_paid',
    amount          DECIMAL(10, 2) NOT NULL,
    ...
    FOREIGN KEY (user_id)  REFERENCES users(id)  ON DELETE CASCADE,
    FOREIGN KEY (event_id) REFERENCES events(id) ON DELETE SET NULL
);
  • ENUM(...) — the column can only hold one of the listed words.
  • ON DELETE CASCADE — delete the user → their bookings are deleted too.
  • ON DELETE SET NULL — delete the event → bookings stay, event becomes empty ("Deleted event").
  • INDEX lines make searching faster (e.g. bookings by user + event).

You never need to run this by hand: the server runs it automatically at start-up.

2.2 Database connection files (config folder)

server/config/db.js

49 lines · the connection to MySQL
  • Creates a pool — a group of ready-made connections to MySQL that all the code shares (faster than connecting every time).
  • Sets every connection to UTC time (SET time_zone = '+00:00') so the times saved by MySQL and by the code match. The website then shows them in Indian time.
  • initDB() — runs at start-up: creates the eventora database if missing, runs schema.sql, then the migrations, then adds default content.
const pool = mysql.createPool({ host, port, user, password, database: DB_NAME, connectionLimit: 10, timezone: 'Z' });
pool.on('connection', (conn) => conn.query("SET time_zone = '+00:00'"));
In simple words: "Keep 10 phone lines open to the database and give one to whoever needs it."

server/config/migrations.js

20 lines · adds new columns to old databases

CREATE TABLE IF NOT EXISTS does not add new columns to a table that already exists. This file checks the database for 5 newer columns (users.is_blocked, users.phone, bookings.payment_method, bookings.payment_ref, bookings.paid_at) and adds any that are missing with ALTER TABLE ... ADD COLUMN. Your existing data is kept.

Adding a new column later? Add it to schema.sql and to the list at the top of this file.

2.3 Models — talking to MySQL (models folder)

A model is a small set of functions for one table. Controllers never write SQL for the main tables directly; they call these functions. Each model also has a "to..." function that converts a database row (e.g. ticket_price) into the shape the website expects (e.g. ticketPrice, plus _id).

2.4 Middleware — the security guard

server/middleware/auth.js

34 lines

Two checks that run before a controller:

  • protect — "are you logged in?" It reads the token from the request header (Authorization: Bearer <token>), verifies it with JWT_SECRET, loads the user from MySQL and attaches it as req.user. If there's no token, a fake token, or the user is blocked, it stops the request (401 or 403).
  • admin — "are you the admin?" Lets the request through only if req.user.role === 'admin'.
const decoded = jwt.verify(token, process.env.JWT_SECRET);
req.user = await User.findById(decoded.id);
if (req.user.isBlocked) {
    return res.status(403).json({ message: 'Your account has been blocked. Contact Project X.', blocked: true });
}
next();   // all good → go to the controller
In simple words: the token is like a wristband you get at the entrance (login). Every time you ask for something private, the guard checks your wristband.

2.6 Controllers — the actual work

Each controller function receives req (the request: body, URL params, logged-in user) and res (used to send the answer). Every function is wrapped in try { ... } catch so an error sends a clean "Server Error" message instead of crashing the server.

server/controllers/authController.js

98 lines · sign up, log in, verify OTP
FunctionStep by step
register1) Check name/email/password are filled. 2) Stop if the email already exists. 3) Hash the password with bcrypt. 4) Save the user as not verified, role always "user" (nobody can make themselves admin). 5) Create a 6-digit OTP and email it.
login1) Find user by email. 2) Compare the password with the hash. 3) If blocked → refuse. 4) If not verified → send a fresh OTP and ask for it. 5) Otherwise send back the user info + a JWT token valid 30 days.
verifyOTP1) Check the code is correct and under 5 minutes old. 2) Refuse if blocked. 3) Mark verified, delete the code, return token (user is now logged in).
const salt = await bcrypt.genSalt(10);
const hashedPassword = await bcrypt.hash(password, salt);   // "password123" → "$2a$10$Xk9..." (can't be reversed)
...
const generateToken = (id, role) => jwt.sign({ id, role }, process.env.JWT_SECRET, { expiresIn: '30d' });
Why hash passwords? Even if someone steals the database, they only see scrambled text, not real passwords. bcrypt can check "is this the right password?" without ever un-scrambling it.

server/controllers/bookingController.js

130 lines · booking rules
FunctionWhat it does
sendBookingOTPCreates a booking OTP for the logged-in user and emails it.
bookEventChecks, in order: OTP valid → event exists → event not in the past → slots left → no existing active booking. Then saves a pending booking with amount = ticket price, and deletes the OTP.
confirmBookingAdmin approves. Uses a transaction with row locks so two admins clicking at the same moment can't give away the same last slot. Sets status confirmed, payment paid/not paid, reduces available_seats by 1, then emails the user.
getMyBookingsUser → their own bookings. Admin → all bookings.
cancelBookingThe owner or admin cancels. If it was confirmed, the slot is given back (+1). Also uses a transaction.
await conn.beginTransaction();
const [[booking]] = await conn.query('SELECT * FROM bookings WHERE id = ? FOR UPDATE', [id]); // lock this row
const [[event]]   = await conn.query('SELECT * FROM events WHERE id = ? FOR UPDATE', [booking.event_id]);
if (event.available_seats <= 0) { await conn.rollback(); return res.status(400)... }
await conn.query("UPDATE bookings SET status = 'confirmed' ...");
await conn.query('UPDATE events SET available_seats = available_seats - 1 WHERE id = ?', [event.id]);
await conn.commit();   // save both changes together, or neither
Transaction in simple words: "Do these steps as one package. If anything fails in the middle, undo everything." This keeps the slot count always correct.

Part 3 — Frontend (client folder)

The frontend is a React app. React builds pages from components — small reusable pieces like a navbar, an event card, or a reel player. A component is just a JavaScript function that returns HTML-like code called JSX.

const Stat = ({ label, value }) => (          // a component with two inputs ("props")
    <div className="card p-5">
        <p>{label}</p>
        <p className="font-display text-4xl">{value}</p>
    </div>
);
<Stat label="Users" value={9} />               // using it

Three React ideas appear in every page:

  • useState — the component's memory, e.g. const [events, setEvents] = useState([]). When you call setEvents(...), the page redraws itself with the new data.
  • useEffect — "do this when the page opens" (or when something changes), e.g. load events from the backend.
  • className="..." — Tailwind CSS styles: short class names like p-5 (padding), text-4xl (big text), bg-brand (red background).

Part 4 — How things work, step by step

These stories follow one action through all the files, so you can see how everything connects.

4.1 Sign up with OTP

  1. User fills name/email/password on Register.jsx and clicks "Join".
  2. AuthContext register() sends POST /api/auth/register.
  3. routes/auth.js → authController.register: checks the email is new, hashes the password, saves the user (not verified).
  4. OTP.replace saves a 6-digit code; email.js emails it (or prints it in the terminal).
  5. User types the code → POST /api/auth/verify-otp → verifyOTP checks it's correct and under 5 minutes old → marks verified → returns a token.
  6. AuthContext saves the token in the browser; the user is logged in and lands on My Tickets.

4.2 Log in

  1. Login.jsx → POST /api/auth/login.
  2. authController.login: user exists? password matches (bcrypt)? not blocked? verified?
  3. Returns { name, email, role, token }. From now on axios.js sends the token with every request automatically.
  4. Admin → /admin; user → /dashboard.

4.3 Booking a spot

  1. On EventDetail.jsx the user clicks "Request my spot" → POST /api/bookings/send-otp (needs login: protect checks the token).
  2. bookingController.sendBookingOTP emails a booking code.
  3. User enters the code → POST /api/bookings with { eventId, otp }.
  4. bookEvent checks: code valid → event exists → event not past → slots left → no double booking.
  5. Booking.create saves a pending, not paid booking with amount = ticket price.
  6. The page shows "You're on the request list". Nothing is charged; no slot is used yet.

4.4 Admin approves & records payment

  1. Admin opens Bookings & Payments → GET /api/admin/bookings (protect + admin).
  2. Clicks Approve · paid → PUT /api/bookings/:id/confirm with { paymentStatus: 'paid' }.
  3. confirmBooking runs a transaction: locks the booking + event, checks a slot is free, sets confirmed + paid (+ paid time), reduces slots by 1, commits.
  4. email.js sends "Booking Confirmed" to the user.
  5. Later, if the user pays by UPI: admin clicks Payment → enters method + UTR/reference → PUT /api/admin/bookings/:id/payment → adminController.updatePayment saves it.
  6. The Overview "Revenue collected" and the Excel file include it straight away.

4.5 Blocking a user

  1. Admin → Users → Block → confirm → PUT /api/admin/users/:id/block with { blocked: true }.
  2. setBlocked refuses if it's you or an admin; otherwise sets is_blocked = TRUE and cancels their pending requests.
  3. The user's next action anywhere hits middleware/auth.js, which answers 403 "blocked".
  4. axios.js sees "blocked", logs them out and shows the Login page with the blocked message. Logging in again is refused by authController.login.
  5. Unblock reverses it (their cancelled requests stay cancelled).

4.6 Uploading photos & reels

  1. GalleryTab.jsx packs the chosen files into a FormData (a "parcel" of files + text) and sends POST /api/gallery, showing the upload %.
  2. routes/content.js: protect + admin → upload.js (multer) checks type and size and saves files to server/uploads/images/ with random names.
  3. contentController.addGallery writes one row per photo in the gallery table with the address /uploads/images/….
  4. The home page loads GET /api/gallery, and mediaUrl() turns the address into http://localhost:5000/uploads/images/… so the browser can show it.
  5. Reels work the same way via POST /api/reels, with the video going to uploads/videos/.

4.7 Playing a reel

  1. Visitor clicks a reel card on Home.jsx → setPlaying(reel) opens ReelPlayer.
  2. Uploaded video? → plays in the site's video player.
  3. Only an Instagram link? → shows Instagram's embedded player. For some reels Instagram shows "Watch on Instagram" instead of playing — that's Instagram's rule, not the site.
  4. "Open on Instagram" button opens the original reel in a new tab.

4.8 Excel download

  1. Admin clicks "Download paid users" → downloadExcel('paid') in ui.jsx → GET /api/admin/export?type=paid with the token.
  2. exportExcel runs 3 SQL queries (paid bookings, revenue per event, users) and builds a workbook with exceljs.
  3. The browser receives the file and saves it as projectx-paid-bookings-YYYY-MM-DD.xlsx.

4.9 Changing the header

  1. Admin edits text or picks a new hero image/video in HeaderTab.jsx → "Save changes" → PUT /api/settings.
  2. contentController.updateSettings saves each setting in the settings table and deletes any replaced upload.
  3. The answer updates SiteContext, so the Navbar announcement bar, the Home hero and the Footer change instantly for you, and for visitors on their next page load.

5.2 Security notes

  • Passwords are hashed with bcrypt — never stored as plain text.
  • Login tokens (JWT) are signed with JWT_SECRET. Use a long random secret in production and never share .env.
  • Every admin action is checked on the server (protect + admin), not just hidden in the website.
  • SQL injection protection: all queries use ? placeholders.
  • Uploads: only image/video types, max 250 MB, random file names, and deletes are limited to the uploads folder.
  • Sign-up can't create admins — role is always "user". Admins are created in the database (or by the seed).
  • Backups: back up the MySQL database and the server/uploads folder together.
  • Payments are recorded by the admin; no card or UPI details are handled by the site.
